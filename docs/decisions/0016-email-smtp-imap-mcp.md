# Решение: Email MCP для IMAP-проверки и SMTP-отправки

- **Дата:** 2026-10-23
- **Выбранный модуль:** [`@codefuturist/email-mcp@0.6.0`](https://github.com/codefuturist/email-mcp)
- **Транспорт:** локальный stdio через `npx`
- **Провайдер AdsMCP:** `email`
- **Конфигурация:** `modules/modules.example.json` и локальный `modules/modules.json`

## Задача

Подключить существующий почтовый ящик так, чтобы AdsMCP мог проверять входящие
письма и отправлять сообщения. Для проверки нужен IMAP, а SMTP сам по себе
покрывает только исходящую почту, поэтому выбран модуль с обоими протоколами.

## Почему выбран этот кандидат

`@codefuturist/email-mcp` лучше всего совпадает с текущей архитектурой AdsMCP:

- Node-совместимый локальный stdio-модуль, который запускается той же схемой `npx`,
  что и остальные внешние MCP;
- IMAP-чтение, поиск, папки, треды и проверка соединения;
- SMTP-отправка, ответ, пересылка и черновики;
- поддержка нескольких аккаунтов и OAuth2 для Gmail/Microsoft 365 в экспериментальном
  режиме;
- TLS/STARTTLS, отсутствие паролей в логах и встроенный rate limit.

Версия закреплена явно (`0.6.0`), чтобы обновление внешнего пакета не меняло
поведение модуля незаметно. Текущий пакет требует Node.js >=24; текущая среда
AdsMCP это поддерживает.

## Рассмотренные альтернативы

| Кандидат | Плюсы | Почему не выбран основным |
| --- | --- | --- |
| [`diskd-ai/email-mcp`](https://github.com/diskd-ai/email-mcp) | Форк с IMAP/SMTP, несколькими аккаунтами и расширенной автоматизацией | Форк той же идеи с более широким surface; для базовой почты лучше держать зависимость на исходном проекте и открывать минимум инструментов |
| [`boutquin/mcp-server-email`](https://github.com/boutquin/mcp-server-email) | Go, MIT, multi-account, connection pooling, OAuth2, 22 инструмента | Нужны Go 1.24+ и отдельный бинарный runtime; это лишняя операционная сложность для Node-проекта |
| [`sandraschi/email-mcp`](https://github.com/sandraschi/email-mcp) | IMAP/SMTP, transactional API, stdio/HTTP и web-dashboard | Python/uv и dashboard расширяют область ответственности; не нужны для сценария «проверить и отправить письмо» |
| [`mailmcp/mailmcp`](https://github.com/mailmcp/mailmcp) | Готовый self-hosted вариант | Лицензия и модель распространения менее удобны для базовой зависимости проекта |

## Разрешённый surface

Разрешены только инструменты для:

- чтения аккаунтов, папок, писем, тредов и статусов;
- поиска писем и проверки здоровья подключения;
- чтения метаданных/содержимого вложений и контактов;
- отправки нового письма, ответа и пересылки;
- сохранения черновика.

В `allow_tools` намеренно не входят удаление, массовые операции, перенос писем,
изменение папок/labels, планирование рассылок, watcher/notifications, clipboard,
календарь и локальные reminder-действия.

## Настройка

1. Скопировать пример манифеста, если локального файла ещё нет:

   ```powershell
   Copy-Item modules/modules.example.json modules/modules.json
   ```

2. Указать в `.env` минимум `MCP_EMAIL_ADDRESS`, `MCP_EMAIL_PASSWORD`,
   `MCP_EMAIL_IMAP_HOST` и `MCP_EMAIL_SMTP_HOST`. Для Gmail и других сервисов
   с MFA использовать app password или OAuth2, а не основной пароль.

3. Проверить план через `ads_module_plan`, затем получить список инструментов через
   `ads_module_tools` с `module_id=email`.

Манифест передаёт в дочерний процесс только перечисленные `MCP_EMAIL_*` и
`EMAIL_ACCOUNTS` переменные. Секреты не записываются в JSON манифеста.
Переменная `MCP_EMAIL_READ_ONLY=true` отключает почтовые write-tools ещё и на
уровне самого внешнего пакета.

## Ограничения

- Реальная отправка письма всё равно является внешним write-действием и должна
  выполняться только после явного подтверждения пользователя.
- OAuth2 в выбранном пакете помечен как experimental; сначала использовать
  app password или отдельный токен, если провайдер это допускает.
- Локальный кэш почты может содержать тела писем и вложения, поэтому каталог данных
  должен оставаться приватным и защищаться шифрованием диска.
